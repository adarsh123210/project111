# Courier Management System — Learning Guide

This document explains how the application works, the algorithms it uses, the data it stores, and the file paths involved. It is factual and concise; it avoids marketing language.

---

## 1. Project Overview

The Courier Management System is a local desktop application for managing courier branches, customers, parcel bookings, tracking, and reports.

- **GUI toolkit:** Tkinter (standard Python library)
- **Database:** SQLite, stored locally as `courier_management.db`
- **Image loading:** Pillow (optional; used on the login screen artwork, with a fallback icon)
- **Roles:** Admin and Staff only. Customer records are sender/receiver profiles, not login accounts.

Entry point: `python main.py`

## 3. How the Application Works

### 3.1 Startup Sequence

1. `main.py` calls `database.initialize_database()`, which creates all tables (if missing) and seeds default admin/staff users, branches, delivery charge rules, and sample customers.
2. `main.py` creates `LoginWindow` (a `tk.Tk`) and enters `mainloop()`.
3. The login screen asks the user to choose **Admin** or **Staff**, enter username and password, then click **Sign In**.
4. On successful authentication, the login window withdraws and opens a `BaseWindow` portal for the matched role.

### 3.2 Window Layout (`views/base_view.py`)

`BaseWindow` extends `tk.Toplevel` and provides:

- A fixed-width sidebar (230 px) with brand header, user badge, navigation buttons, and a Logout button.
- A content area to the right where the current page frame is packed.
- Navigation buttons highlight when active and show a hover color on mouse enter/leave.
- `add_nav_item(text, page_creator_fn)` registers a sidebar button that switches pages by calling `page_creator_fn(content_area)`.
- `_bind_button_highlights()` applies hover/active colors to buttons inside each page.
- `add_treeview_scrollbars(tree)` attaches vertical and horizontal scrollbars to any `ttk.Treeview`.

### 3.3 Role Routing (`views/login_view.py`)

After authentication, `_launch_user_module(user)` opens the correct portal:

| Role | Portal Class | File |
|------|-------------|------|
| Admin | `BaseWindow("Admin & Management Control Panel", ...)` | `views/admin/admin_views.py` |
| Staff | `BaseWindow("Staff & Branch Management Portal", ...)` | `views/staff/staff_views.py` |

Admin gets 9 navigation items; Staff gets 4. Both roles share Parcel Tracking.

### 3.4 Database Access Pattern

Every model function in `models/db_models.py` follows the same pattern:

1. Call `database.get_connection()` to open a SQLite connection with `row_factory = sqlite3.Row` (dict-like row access) and `PRAGMA foreign_keys = ON`.
2. Execute the SQL query with parameterized placeholders (`?`).
3. Convert rows to `dict` objects.
4. Close the connection.
5. Return the data (or `(result, error)` tuple for write operations).

Write operations wrap SQL in `try/except` with `conn.rollback()` on failure and `conn.close()` in `finally`.

## 4. Algorithms Used

### 4.1 Password Hashing (`utils/helpers.py`)

- **Algorithm:** SHA-256 hex digest of the UTF-8 encoded password.
- **Functions:** `hash_password(password)` and `verify_password(password, hashed_password)`.
- **Usage:** Passwords are hashed before storage in `users.password_hash`. Authentication compares the hash of the entered password against the stored hash.
- **Note:** This is a plain hash with no salt or key stretching. It is suitable only for a local learning/demo application, not for production security.

### 4.2 Tracking Number Generation (`utils/helpers.py`)

- **Format:** `CMS-YYYY-XXXXXX`
- **Algorithm:** Takes the current year and appends a 6-digit random integer (`100000`–`999999`).
- **Uniqueness check:** `create_parcel()` in `models/db_models.py` queries `parcels` for the generated number and regenerates if a collision occurs, looping until a unique number is found.

### 4.3 Delivery Charge Calculation (`utils/helpers.py`)

`calculate_delivery_cost(parcel_type, weight_kg, is_express, distance_km, charge_rules)`:

1. Match the parcel type against the provided charge rules list (case-insensitive). Fall back to defaults if no rule matches.
2. Compute:
   - `weight_cost = weight_kg * per_kg_rate`
   - `distance_cost = distance_km * per_km_rate`
   - `subtotal = base_charge + weight_cost + distance_cost`
3. Apply express multiplier only if `is_express` is true.
4. Return a dict with `base_charge`, `weight_cost`, `distance_cost`, `express_surcharge`, and `total`, each rounded to 2 decimal places.

### 4.4 Date Range Filtering (`models/db_models.py`)

Reports and date-filtered queries use SQLite `date()` comparison:

```sql
WHERE date(column) BETWEEN date(?) AND date(?)
```

This normalizes stored datetime strings to date-only for inclusive range matching.

### 4.5 Parcel Status Lifecycle

Statuses are stored as text and updated via `update_parcel_status()`:

- `Booked` → `Picked Up` → `In Transit` → `At Branch` → `Out for Delivery` → `Delivered` / `Failed` / `Returned to Sender` / `Cancelled`

When status becomes `Delivered`, `delivered_at` is set to the current timestamp. Each status change inserts a row into `tracking_events`.

### 4.6 Branch Transfer (`models/db_models.py`)

`transfer_parcel_branch()` performs three operations atomically (with rollback on failure):

1. Insert into `branch_transfers` with status `In Transit`.
2. Update `parcels.current_branch_id` to the destination and set parcel status to `In Transit`.
3. Insert a tracking event recording the transfer route.

## 5. Data Shared / Database Schema

All data lives in `courier_management.db` (SQLite). Tables and their purpose:

| Table | Purpose |
|-------|---------|
| `users` | Login accounts: username, password hash, role (admin/staff), active state, created timestamp |
| `staff` | Staff profiles linked to a `users` row, with branch assignment, employee ID, phone, email |
| `couriers` | Legacy courier records (retained; no courier login or screens) |
| `branches` | Branch details: code, name, address, city, state, pincode, phone, manager, active state |
| `customers` | Sender/receiver contact and address profiles |
| `parcels` | Core parcel record: tracking number, sender/receiver IDs, type, weight, dimensions, source/dest/current branch, status, total charge, booked by, timestamps |
| `tracking_events` | Status history per parcel: status, location, remarks, updater, timestamp |
| `branch_transfers` | Inter-branch parcel movement records |
| `transactions` | Payment records: parcel, amount, method, status, recorded by, date |
| `delivery_charges` | Rate card: base charge, per-kg, per-km, express multiplier by parcel type |
| `audit_log` | Action history: user, table, record ID, old/new values, timestamp |

### Key Relationships

- `users` → `staff` (one-to-one via `user_id`)
- `branches` → `staff` (many-to-one via `branch_id`)
- `branches` → `parcels` (source, destination, current)
- `customers` → `parcels` (sender and receiver)
- `users` → `parcels` (booked_by)
- `couriers` → `parcels` (assigned_courier_id, legacy)
- `parcels` → `tracking_events` (one-to-many, cascade delete)
- `parcels` → `branch_transfers` (one-to-many, cascade delete)
- `parcels` → `transactions` (one-to-one/one-to-many, cascade delete)
- `users` → `transactions` (recorded_by)

### Sample Seed Data

- Staff user: `staff` / `staff123`
- 4 branches: Mumbai, Delhi, Bangalore, Pune
- 4 delivery charge rules (Document, Package, Fragile, Heavy)
- 3 sample customers

## 8. Summary of Data Flow

```
User input (Tkinter view)
        ↓
View calls model function (models/db_models.py)
        ↓
Model opens SQLite connection (database.get_connection)
        ↓
Model executes parameterized SQL
        ↓
Model returns dict or (result, error) tuple
        ↓
View updates UI (messagebox, table refresh, dialog)
```

All database access is synchronous and blocking on the main Tkinter thread. There is no background threading, networking, or external API usage.
